# Mutation testing (Cosmic Ray 8.9.0)

Tool choice: Cosmic Ray. mutmut needs `fork()` and does not run on native Windows; Cosmic Ray runs here and supports custom operators.
Method: mutants run in an isolated copy of the repo (`scripts/setup_mutation_workdir.sh`) so the real tree is never mutated.
Test command: team unit tests (rules, coverage, MCC, killer tests) with a reusable on-disk test DB (`tests/team/settings_mutation.py`).
Kill rate = killed / (killed + survived + timeout). "Incompetent" mutants (invalid code) are excluded.
Raw data (all real): `reports/mutation/round{1,2}_*.jsonl|sqlite`; per-mutant analysis: `reports/mutation/survivor_analysis.csv`
(generated by `scripts/build_survivor_table.py`).

## Scope: three business-logic modules, 415 mutants
| Module | Mutants | Round 1 (before killer tests) | Round 2 (after) |
|---|---|---|---|
| `core/signup/flow/participant_validation.py` | 117 | 106 killed, 10 survived -> **91.4 %** | 114 killed, 2 survived -> **98.3 %** |
| `plugins/baseshiftstructures/structure/common.py` | 165 | 119 killed, 42 survived -> **73.9 %** | 152 killed, 9 survived -> **94.4 %** |
| `core/signup/stats.py` | 133 | 93 killed, 40 survived -> **69.9 %** | 133 killed, 0 survived -> **100 %** |
| **Total** | 415 | 318 killed, 92 survived -> **77.6 %** | 399 killed, 11 survived, 5 incompetent -> **97.3 %** |

Round 2 reran only the 92 round-1 survivors (survivor results deleted from a copy of the session; Cosmic Ray reruns the rest).
This is valid because tests were only added: a mutant killed by an existing test stays killed.
Statement and branch coverage was already 100 % on all three modules before round 1: **100 % coverage still allowed 92 behavioural gaps.**

## Custom operators (`tools/team_mutation/`)
| Operator | Business rule | Mutants | Outcome |
|---|---|---|---|
| `team/RaiseToReturn` | error signalling (the DEFECT-001 class) | 12 | 10 killed, 2 incompetent |
| `team/StateConstantSwap` | BR3 participation states | 20 | 20 killed |
| `team/RuleBoundaryShift` | BR1/BR4/age boundaries | 3 | 3 killed |

None of our custom mutants survived. That shows the tests are strong against these specific rule violations, but also that
the operators are narrow (RuleBoundaryShift matched only 3 comparisons) - the survivors all came from generic core operators.
The strong spot is deliberate: BR1-BR4 were designed with BVA, a decision table and state transitions before mutation ran.

## Analysis of the 92 round-1 survivors (all analysed; full table in the CSV)
| Category | Count | Meaning |
|---|---|---|
| Killable - missing test or weak assertion | 81 | killed in round 2 by tests named in the CSV rationale |
| Equivalent | 11 | still alive after targeted tests; justified below |

Root causes of the 81 (for the defect/RCA section): (1) tests used zeros and tiny numbers where bitwise operators equal addition
(1+2 = 1|2 = 1^2; 3-1 = 3^1) - 40 `stats.py` mutants and several in `common.py`; (2) optional/boundary form fields never tested with
empty or limit values; (3) default parameters never exercised because the caller always passes every argument; (4) only one participation
state tested where the code distinguishes five; (5) an event-detail test that only asserted the page title.

### The 11 equivalent mutants
| Module:line | Mutation | Why equivalent |
|---|---|---|
| participant_validation:47 (x2) | negate `if not shift.event.active` | **Masked by DEFECT-001**: the checker returns its error instead of raising, so the outcome is discarded. Becomes killable after the fix. |
| structure_common:14 | `TYPE_CHECKING` switch | typing-only; classes inherit the base anyway |
| structure_common:83, 84, 176 (x3) | `-1` offsets in `max(0, x)`, `x or -1`, `max(x or 0, y or 0)` | result is clamped to >= 0 by the surrounding `max` / `range` |
| structure_common:134 | remove `@staticmethod` | method is always called through the class, never bound |
| structure_common:177 (x3) | `<` to `<=`, `!=`, `is not` | `list * n` with n <= 0 is empty, so outcomes are identical |

## CI gate threshold (justified from this evidence)
Gate: kill rate on `participant_validation.py` >= **90 %** (`scripts/check_mutation_score.py --min 90`, job `mutation-score`).
Round 1 gave 91.4 % and round 2 gives 98.3 %, so 90 % blocks a real regression (a deleted killer test drops it below) without failing on the
2 known equivalent mutants. A 100 % gate would be impossible because equivalent mutants exist.

## Limitations
- Mutation was run on three modules, not the whole app (about 1 hour per 300 mutants on this machine).
- Equivalence of the 11 survivors is argued by reading the code, not formally proven.
- Cosmic Ray core operators were used unfiltered; some generated mutants (e.g. bit-shift for `+`) are unrealistic.
